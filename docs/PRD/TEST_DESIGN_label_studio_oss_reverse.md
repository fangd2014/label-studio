# Label Studio OSS 测试设计文档

## 1. 文档信息
- 文档类型：测试设计（Test Design / Test Strategy）
- 关联文档：`docs/PRD/PRD_label_studio_oss_reverse.md`、`docs/PRD/SDD_label_studio_oss_reverse.md`
- 适用仓库：`label-studio`
- 版本：`v1.0`
- 日期：`2026-04-01`

## 2. 测试目标
1. 验证 FR-01 ~ FR-20 的功能正确性、稳定性和可回归性。
2. 验证主链路“项目创建 -> 数据导入 -> 标注执行 -> 质量控制 -> 导出集成”的端到端可用性。
3. 验证认证鉴权、组织隔离、外部依赖调用的安全性与一致性。
4. 建立可持续自动化回归资产，支撑后续迭代快速发布。

## 3. 测试范围

### 3.1 范围内
1. 组织与用户管理。
2. 项目与标注配置管理。
3. 数据导入、Data Manager、任务分配、标注/草稿/预测管理。
4. 质量统计、ML 联动、存储集成、导出、Webhook。
5. 认证会话、FSM 审计、健康检查与 API schema。
6. 关键 NFR：性能、容量、并发一致性、安全防护。

### 3.2 范围外
1. 企业版专属能力。
2. 前端视觉/文案层面的主观体验测试。
3. 第三方服务本身可用性（仅验证集成逻辑与故障处理）。

## 4. 测试对象与层次

| 层次 | 目标 | 主要工具建议 | 通过标准 |
|---|---|---|---|
| 单元测试 | 关键函数、策略分支、校验逻辑 | `pytest` | 核心模块通过率 100% |
| API 集成测试 | DRF 接口与数据库读写一致性 | `pytest + APIClient` | P0/P1 接口零阻断缺陷 |
| 端到端流程测试 | 核心业务链路完整性 | API 编排 + 少量 UI 验证 | 主链路全绿 |
| 非功能测试 | 性能、并发、安全、可靠性 | 压测工具 + 安全测试脚本 | 指标达到准出阈值 |

## 5. 测试环境设计

### 5.1 环境分层
1. DEV：开发自测环境，快速反馈。
2. SIT：系统集成测试环境，执行全链路回归。
3. UAT：业务验收环境，执行场景验收与发布前确认。

### 5.2 环境要求
1. 数据库：PostgreSQL（版本与生产保持一致）。
2. 缓存/异步：Redis + 异步任务执行组件。
3. 存储模拟：S3/GCS/Azure 至少一类真实或模拟环境。
4. ML Backend：提供可控 mock 服务与健康检查接口。
5. Webhook 接收端：可记录 payload、header、重试次数。

### 5.3 测试数据
1. 基础数据：组织、管理员、项目负责人、标注员、算法工程师。
2. 任务数据：文本、图像、音频、视频、PDF、CSV/JSON 混合数据集。
3. 异常数据：超大文件、非法扩展名、坏格式、外部 URL 不可达。
4. 容量数据：10k、100k 级任务规模。

## 6. 测试方法与策略

### 6.1 功能测试策略
1. 按模块分层设计用例：正向、逆向、边界、异常。
2. 每个 FR 至少 1 个 P0 用例。
3. 对任务状态、队列、锁、重叠标注策略进行分支覆盖。

### 6.2 集成测试策略
1. 导入 -> next task -> 标注 -> summary -> 导出 -> webhook 完整链路。
2. ML 与存储作为外部依赖进行成功和失败双场景验证。

### 6.3 回归测试策略
1. 构建 P0（阻断级）每日回归集。
2. 构建 P1（高价值）每次合并回归集。
3. 构建 P2（扩展/边缘）每周全量回归集。

### 6.4 安全测试策略
1. 认证鉴权：未登录访问、越权访问、跨组织访问。
2. 输入安全：扩展名白名单、上传大小、URL SSRF 防护。
3. 会话安全：JWT 刷新/失效、token 重置后旧 token 失效。

### 6.5 性能与可靠性策略
1. 导入吞吐与内存峰值监控。
2. 任务分页查询延迟和数据库慢查询观察。
3. next task 并发冲突率与锁生效验证。
4. webhook 大量事件投递成功率与重试行为验证。

## 8. 自动化策略

### 8.1 分层自动化
1. API 自动化：覆盖所有 P0/P1 接口与关键异常分支。
2. 作业自动化：导入/导出异步状态与失败重试路径。
3. 性能自动化：关键接口基线压测脚本纳入 CI 定时任务。

### 8.2 自动化优先级
1. 第一优先：`import`、`next task`、`annotations`、`export`、`auth`。
2. 第二优先：`ml`、`storages`、`webhooks`。
3. 第三优先：低频管理类接口与扩展动作。

### 8.3 建议目录结构
1. `label_studio/tests/api/test_projects.py`
2. `label_studio/tests/api/test_imports.py`
3. `label_studio/tests/api/test_tasks_next.py`
4. `label_studio/tests/api/test_annotations.py`
5. `label_studio/tests/api/test_exports.py`
6. `label_studio/tests/api/test_security_auth.py`

## 9. 缺陷管理策略
1. 缺陷分级：S0（阻断）、S1（高）、S2（中）、S3（低）。
2. 缺陷字段：模块、环境、步骤、期望/实际、日志、请求响应、影响范围。
3. 关闭标准：修复 + 回归通过 + 无新增副作用。

## 10. 测试准入与准出

### 10.1 准入标准
1. PRD/SDD 已冻结当前测试范围。
2. 核心接口可访问，测试环境可用。
3. 基础测试数据准备完成。

### 10.2 准出标准
1. P0 用例通过率 100%。
2. P1 用例通过率 >= 95%。
3. 无未关闭 S0/S1 缺陷。
4. 关键性能指标达标：
5. `GET /api/tasks` P95 满足目标阈值。
6. 导入成功率、导出成功率、Webhook 成功率满足目标阈值。

## 11. 测试里程碑建议
1. M1：接口与主流程基线测试资产建立。
2. M2：高并发/高容量场景专项验证。
3. M3：自动化回归集稳定运行与发布门禁接入。

## 12. 风险与应对
1. 风险：外部依赖不稳定导致测试波动。
2. 应对：引入 mock 服务与重试策略，拆分“依赖可用性”与“集成逻辑”验证。
3. 风险：大数据量测试耗时长。
4. 应对：分层样本集 + 夜间回归 + 周期性全量压测。
5. 风险：需求边界变化快，造成用例失效。
6. 应对：建立 FR 与 TC 双向追踪，需求变更即更新用例映射。
