# 二期设计：工作区与项目级角色（中文优先）

## 目标
在现有组织模型上引入“工作区”作为项目分组边界，并为后续项目级角色（Annotator/Reviewer）提供可扩展的数据基础。全流程保持中文可见（默认命名、错误提示、文档）。

## 备选方案

1. 工作区先行（推荐）
- 内容：先上 Workspace 模型、项目归属、基础 API。
- 优点：低风险、可快速验证、对后续角色治理提供稳定边界。
- 风险：角色能力暂未落地，需要后续迭代。

2. 角色先行
- 内容：先扩展 ProjectMember.role 并做权限拦截。
- 优点：角色功能更早可见。
- 风险：缺少工作区边界，后续可能返工权限策略。

3. 双线并行
- 内容：工作区和角色同一迭代同时落地。
- 优点：一次性功能更完整。
- 风险：复杂度和回归范围显著提升，不利于“每步可验证”。

## 选型
采用方案 1：工作区先行。

## 分阶段范围

### Step 1（本次落地）
- 新增 Workspace 模型（组织内唯一默认工作区）
- 新组织自动创建默认工作区（中文名“默认工作区”）
- Project 增加 workspace 关联并自动绑定默认工作区
- 新增组织工作区列表/创建 API
- 新增中文错误提示：跨组织创建工作区时报错中文
- 测试覆盖：工作区 API + 项目默认绑定

### Step 2（下一步）
- 扩展 ProjectMember.role（annotator/reviewer/manager）
- 项目成员管理 API 增加角色读写
- 数据迁移：历史成员默认 annotator
- 测试覆盖：角色赋值与查询

### Step 3
- 角色驱动权限收口（任务流、评审流、数据管理）
- 引入最小权限矩阵及回归测试

### Step 4
- 前端“工作区筛选 + 角色展示”中文化增强
- 补齐端到端验证脚本

## 验证标准（每步）
- 数据结构可迁移
- API 可调用且返回稳定
- 至少 1 组新增测试通过
- 提供可复现命令（pytest/curl）
